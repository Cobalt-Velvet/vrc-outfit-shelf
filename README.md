# vrc-outfit-shelf

VRChat向けのアセット管理サービス。購入したアセットと、それをどのアバターに使えるかを記録します。

**デモ:** https://vrc-outfit-shelf.onrender.com

無料プランで公開しているため、しばらくアクセスがないとサーバーが停止します。停止後の最初のアクセスは、表示まで50秒以上かかることがあります。2回目以降は通常の速さで表示されます。

デモでは誰でも会員登録して試せます。登録した内容はログイン中の利用者にだけ表示されます。

## なぜ作ったか

VRChatで活動する中で、「以前買ったアセットがどこにあるか分からない」「どのアバターに適用したのか分からない」という声を周りから何度も聞きました。困りごとは「何を持っているか」と「それをどこにどう使ったか」の二つに分かれるため、この二つを別々に記録し、後から結びつけられる構造を前提に設計しています。

## 技術構成

- アプリケーション: Go（net/http, html/template, pgx, bcrypt）
- 画面のスタイル: Water.css（classless CSS）
- データベース: PostgreSQL
- 開発環境: Docker Compose
- 公開環境: Render（アプリケーション）/ Neon（PostgreSQL）

## 現在の状態

以下を実装し、公開しています。

- データベースの設計・構築とシードデータ
- 会員登録（パスワードは bcrypt でハッシュ化して保存）
- セッション方式のログイン・ログアウト
- ログインが必要なページの保護（未ログインの場合はログイン画面へ移動）
- アセットの一覧表示・登録・編集・削除（ログイン中の利用者のアセットのみ）
- アバターの一覧表示・登録・詳細表示（ログイン中の利用者のアバターのみ）
- アバターの詳細画面で、自分のアセットを選んで対応付ける機能
- 他人のアセット・アバターや存在しないものには 404 を返す所有権チェック
- トップページ（`/`）
- html/template による画面描画と、Water.css による画面のスタイル
- ハンドラーのテスト（23件）
- Render と Neon へのデプロイ

プリセットと改変履歴は、今後追加する予定です。

## 使い方の流れ

1. トップページから会員登録し、ログインすると、アバター一覧に移動します
2. アバター一覧でアバターを、アセット一覧でアセットを、それぞれ登録します
3. アバターの詳細画面で、自分のアセットの中から対応するものを選んで対応付けます（アセットを1件も登録していない場合は、選択欄の代わりにアセット一覧への案内が表示されます）

アセットとアバターを別々に登録してから結びつけるのは、一つのアセットが複数のアバターに対応し、一つのアバターにも複数のアセットが対応する（多対多の）関係だからです。

## 設計上の判断

### 認証

- 認証は JWT ではなくセッション方式を採用しました。サーバー1台・サーバーサイドレンダリングの構成では JWT の利点が生きず、ログアウトを確実に処理できるためです
- ログアウト時はセッションをデータベースから削除します。Cookie を消すだけでは、そのセッションIDが有効期限（ログインから7日）まで使えてしまうためです
- セッションIDは crypto/rand で生成し、Cookie には HttpOnly と SameSite=Lax を付けています
- Secure 属性は、環境変数 `COOKIE_SECURE` が `true` のときだけ付けます。Secure を付けた Cookie はブラウザが HTTPS でしか送らないため、HTTP で動かすローカル環境では付けず、HTTPS で公開している環境でだけ有効にしています。公開先のサービスでは HTTPS の処理がアプリケーションの手前で終わり、アプリケーションからはリクエストが HTTP に見えるため、リクエストから判断せず環境変数で切り替えています
- セッションの作成・確認・削除は session.go にまとめています。Cookie の属性を一か所で管理し、作成時と削除時で属性が食い違わないようにするためです。ログインとログアウトのハンドラーは、結果に応じた画面の移動だけを担当します
- ログイン確認は各ハンドラーに書かず、ミドルウェア（requireLogin）の一か所にまとめています。確認したユーザーIDはリクエストの context に入れてハンドラーへ渡します。グローバル変数に置くと、同時に届いたリクエストの間で値が混ざるためです
- ログアウトは POST で受け付けます。HTTP では GET はサーバーの状態を変えないメソッドとされており、GET にすると他のサイトのリンクを開いただけでログアウトさせられるためです
- ログイン失敗時は「ユーザーが存在しない」と「パスワードが違う」を区別せず、同じメッセージとステータスコードを返します
- 会員登録で名前が重複した場合は 409 を返します。名前がそのままログインIDになる構造のため、その名前が登録済みかどうかが分かってしまう点はトレードオフとして受け入れています

### データ設計

- アバターとアセットは一つのテーブルにまとめず、分けています。まとめると、対応関係・プリセット・改変履歴で「アバターでなければならない」という制約をデータベース側で表現できなくなるためです
- 他人のアバターに他人のアセットを結びつけられないようにする利用者の境界は、アプリケーション側で検査する方針です。データベースの複合外部キーで表すには中間テーブルにも利用者IDを持たせる必要があり、データの持ち方が冗長になるためです

### 所有権チェック

- アセットの編集・削除は、URL のアセットIDとログイン中の利用者IDの両方を WHERE の条件に入れた1つの SQL で行い、対象の行が0件なら 404 を返します。URL の番号は誰でも書き換えて送れるため、番号だけを条件にすると他人のアセットを操作できてしまうためです
- 他人のアセットと存在しないアセットは区別せず、どちらも 404 を返します。403 を返すと、そのIDのアセットが存在することが分かってしまうためです。ログイン失敗時に二つの原因を区別しないのと同じ考え方です
- 編集画面やアバターの詳細画面を表示するとき（GET）も、同じ条件で取得します。表示だけでも、条件を省くと他人のデータの内容を見られてしまうためです
- 削除や対応付けのようにデータを変える操作は POST のフォームで受け付け、画面の移動は GET のリンクにしています。ログアウトと同じ考え方です

### 対応付け

- アセットとアバターの対応付けは、`INSERT ... SELECT ... WHERE EXISTS (アバターの所有者確認) AND EXISTS (アセットの所有者確認)` の1つの SQL で行います。フォームから届くアセットIDも、URL のアバターIDも書き換えて送れるため、両方が自分のものであるときだけ行を追加します
- 追加された行が0件なら、どちらかが他人のものか存在しないものなので 404 を返します
- すでに対応付けられている組み合わせを再度送った場合は、主キーの重複エラー（SQLSTATE 23505）を受け取り、エラーにせず詳細画面へ戻します（303）。同じ操作を何度行っても結果が同じになるようにするためです
- 重複を `ON CONFLICT DO NOTHING` で無視する方法は使っていません。その方法では重複した場合も追加0件になり、所有権チェックに失敗した場合と区別できなくなるためです

### 画面

- 画面は html/template で描画し、利用者の入力を自動でエスケープすることで XSS を防いでいます
- アバターの詳細画面では、登録されたショップURLをリンクとして表示します。html/template は `href` に入る値を URL として検査し、`javascript:` のような危険な形式を無効な値に置き換えるため、利用者が入力した URL をそのままリンクにしても、スクリプトは実行されません
- HTML は header・nav・main・h1 などの要素で構造を表し、見た目の指定（class 属性）を書いていません。そのため、class を使わずに要素そのものに見た目を付ける classless CSS（Water.css）を、ファイルを1つ読み込むだけで適用できます。後から自作の CSS に替える場合も、HTML を変えずに CSS ファイルを差し替えるだけで済みます
- CSS は外部の配信サービス（CDN）から読み込まず、リポジトリの static/ に置いて、アプリケーション自身が配信しています（`http.FileServer` と `http.StripPrefix`）。外部サービスが止まっても画面のスタイルが崩れないようにするためです。static/ の中身はログインなしで誰でも取得できるため、公開してよいファイルだけを置いています
- トップページは `GET /{$}` で登録しています。`GET /` と書くと、他のどのルートにも当てはまらないすべてのパスに一致してしまい、存在しない URL でも 404 にならずトップページが表示されるためです
- 必須の入力欄には HTML の `required` を付け、送信前にブラウザで空欄を知らせます。ただし、ブラウザの検査は利用者側で外せるため、サーバー側でも空欄を検査して 400 を返します
- アバターの詳細画面で、アセットを1件も登録していない利用者には、選択欄ではなくアセット一覧への案内を表示します。空の選択欄のまま送信すると、アセットIDが空の値で届き、400 になってしまうためです
- カテゴリの選択肢は、画面には日本語で表示し、送信する値（`value`）は英語のまま（clothing など）にしています。データベースに保存する値と表示する文字を分け、表示を変えても保存済みのデータに影響しないようにするためです

### テスト

- ハンドラーは、httptest で作ったリクエストとレコーダーを渡して直接呼び出し、ステータスコードなどを確認しています
- テストは、データベースに触れる前に処理が終わる経路（入力が空の場合、Cookie がない場合）と、データベースを使う経路（会員登録・ログイン、アセットの編集・削除、アバターの登録、対応付け）に分けています。前者はデータベースなしで実行できます
- データベースを使うテストは、開発用とは別のテスト用データベース（Docker Compose の testdb、ポート 5433）に接続します。各テストの開始時にデータを消すため、開発用と同じデータベースを使うと開発中のデータまで消えてしまうためです
- 各テストの開始時に `TRUNCATE users RESTART IDENTITY CASCADE` で全テーブルのデータを消し、IDの採番も戻しています。前に実行したテストのデータが残っていると、同じ名前で登録するテストが重複エラーになるなど、結果が実行順に左右されるためです
- テスト用データベースの接続先は環境変数 TEST_DATABASE_URL で指定します。設定されていない場合はデータベースを使うテストをスキップするため、テスト用データベースがない環境でも `go test ./...` は失敗しません
- ログイン失敗のテストは、「ユーザーが存在しない」場合と「パスワードが違う」場合を別々に用意しています。どちらも同じ 401 を返しますが、サーバー内では別の分岐を通るため、片方のテストだけではもう一方の分岐を確認できないためです
- 入力チェックは、両方が空の場合に加えて「名前だけ空」「パスワードだけ空」も別々に確認しています。両方が空の場合だけでは、条件の `||` を `&&` と書き間違えても気づけないためです
- requireLogin のテストでは、ステータスコードとリダイレクト先に加えて、次のハンドラーが呼ばれていないことも確認しています。リダイレクトした後に処理が止まらず次のハンドラーまで実行されてしまう不具合は、ステータスコードとリダイレクト先だけでは見分けられないためです
- アセットの編集・削除のテストは、所有者が操作する場合と所有者以外が操作する場合の両方を用意しています。所有者以外の場合は、ステータスコード（404）に加えて、データベースの行が残っていること・値が変わっていないことも確認しています。行を削除した後に 404 を返してしまうような不具合は、ステータスコードだけでは見分けられないためです
- 対応付けのテストは、成功する場合、アセットが他人のものの場合、アバターが他人のものの場合、同じ組み合わせを2回送る場合の4つを用意しています。所有者の確認は2つの EXISTS に分かれているため、他人のものの場合をアセット側とアバター側で別々に確認しないと、片方の条件が消えても気づけないためです。いずれも、ステータスコードに加えて対応付けの行数を数えて確認しています
- これらのテストはルーティングを通さずにハンドラーを直接呼ぶため、URL のIDは `SetPathValue` で、ログイン中の利用者IDは context で渡しています。`SetPathValue` を省くとIDが空のまま数値への変換で 404 になり、所有権チェックまで届かないまま「所有者以外は 404」のテストが通ってしまうためです
- 所有権チェックの条件（削除の利用者IDの条件、対応付けのアセット側・アバター側の EXISTS）と重複時の処理を一時的に外し、それぞれ対応するテストが失敗することを確認しています。テストがこれらの不具合を実際に検出できることを確かめるためです

## 動かし方（ローカル環境）

```bash
# 1. .env を用意（.env.example をコピーし、パスワードを設定）
cp .env.example .env
# .env の中身:
#   POSTGRES_PASSWORD=任意のパスワード（開発用データベース）
#   TEST_POSTGRES_PASSWORD=任意のパスワード（テスト用データベース）

# 2. データベースを起動（開発用の db とテスト用の testdb が起動します）
docker compose up -d

# 3. スキーマとシードデータを投入
docker compose exec -T db psql -U seolhui -d maindb < schema.sql
docker compose exec -T db psql -U seolhui -d maindb < seed.sql

# 4. 接続情報を環境変数に設定（パスワードは .env と同じもの）
export DATABASE_URL="postgres://seolhui:<password>@localhost:5432/maindb"

# 5. サーバーを起動
go run .
```

PowerShell の場合は 3 と 4 を以下に置き換えてください。

```powershell
Get-Content schema.sql | docker compose exec -T db psql -U seolhui -d maindb
Get-Content seed.sql | docker compose exec -T db psql -U seolhui -d maindb
$env:DATABASE_URL = "postgres://seolhui:<password>@localhost:5432/maindb"
```

起動後、以下のページで確認できます。

- トップページ: http://localhost:8080/
- 会員登録: http://localhost:8080/signup
- ログイン: http://localhost:8080/signin
- アバター一覧・登録: http://localhost:8080/avatars（ログインが必要です。各アバターの名前から詳細画面へ移動でき、詳細画面で自分のアセットを対応付けられます）
- アセット一覧・登録: http://localhost:8080/assets（ログインが必要です。各アセットの「編集」から編集画面へ移動でき、「削除」で削除できます）

ログアウトは、ログイン後の各画面のメニューにある「ログアウト」ボタンから行えます。

シードデータのユーザーはパスワードが設定されていないためログインできません。動作確認の際は、先に会員登録をしてからログインしてください（会員登録が終わるとログイン画面に移動し、ログインするとアバター一覧に移動します）。一覧にはログイン中の利用者が登録したものだけが表示されるため、会員登録した直後の一覧は空です。

### 環境変数

| 名前 | 用途 | 設定しない場合 |
|---|---|---|
| `DATABASE_URL` | PostgreSQL の接続先 | 起動できません |
| `PORT` | サーバーが待ち受けるポート | 8080 |
| `COOKIE_SECURE` | `true` のとき、セッション Cookie に Secure 属性を付ける | Secure を付けない（ローカル環境向け） |

`COOKIE_SECURE` は小文字の `true` のときだけ有効になります。

## テスト

テストは以下で実行できます。テスト用データベースを用意していない場合、データベースを使うテストはスキップされます。

```bash
go test ./...
```

データベースを使うテストも実行する場合は、テスト用データベースにスキーマを投入し、接続情報を TEST_DATABASE_URL に設定してください（パスワードは .env の TEST_POSTGRES_PASSWORD と同じもの）。

```bash
docker compose exec -T testdb psql -U seolhui -d testdb < schema.sql
export TEST_DATABASE_URL="postgres://seolhui:<password>@localhost:5433/testdb"
go test -count=1 ./...
```

PowerShell の場合:

```powershell
Get-Content schema.sql | docker compose exec -T testdb psql -U seolhui -d testdb
$env:TEST_DATABASE_URL = "postgres://seolhui:<password>@localhost:5433/testdb"
go test -count=1 ./...
```

`-count=1` は、テスト結果のキャッシュを使わずに毎回実行するための指定です。testdb には名前付きボリュームを設定していないため、`docker compose down` でコンテナを削除した後はスキーマを再投入してください。

## デプロイ

公開環境は、費用がかからない無料プランで構成しています。

| | サービス | リージョン |
|---|---|---|
| アプリケーション | Render（Web Service, Free） | Singapore |
| データベース | Neon（Free） | Singapore |

アプリケーションとデータベースを同じリージョンに置き、その間の通信時間を短くしています。日本から近いリージョンのうち、両方のサービスで選べるのが Singapore でした。

Render の設定:

- Language: Go
- Build Command: `go build -tags netgo -ldflags '-s -w' -o app`
- Start Command: `./app`
- 環境変数: `DATABASE_URL`（Neon の接続文字列）、`COOKIE_SECURE=true`

`PORT` は Render が自動で設定するため、指定していません。データベースのスキーマは、Neon の SQL Editor で schema.sql を実行して作成しています。

無料プランの制約として、Render はアクセスがない状態が15分続くと停止し、Neon も5分続くと停止します。そのため、停止後の最初のアクセスは表示まで時間がかかります。
