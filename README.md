# vrc-outfit-shelf

VRChat向けのアセット管理サービス。購入したアセットと、それをどのアバターにどう使ったかを記録します。

## なぜ作ったか

VRChatで活動する中で、「以前買ったアセットがどこにあるか分からない」「どのアバターに適用したのか分からない」という声を周りから何度も聞きました。困りごとは「何を持っているか」と「それをどこにどう使ったか」の二つに分かれるため、この二つを別々に記録し、後から結びつけられる構造を前提に設計しています。

## 技術構成

Go / PostgreSQL / Docker Compose（pgx, net/http, html/template, bcrypt）

## 現在の状態

開発中です。現在までに以下を実装しています。

- データベースの設計・構築とシードデータ
- 会員登録（パスワードは bcrypt でハッシュ化して保存）
- セッション方式のログイン・ログアウト
- ログインが必要なページの保護（未ログインの場合はログイン画面へ移動）
- アセットの一覧表示・登録（ログイン中の利用者のアセットのみ）
- html/template による画面描画
- ハンドラーのテスト（入力が空の場合・未ログインの場合に加え、テスト用データベースを使った会員登録・ログインの成功と失敗）

今後は、アバター・プリセット・対応関係のAPIと所有権チェック、画面の整備、デプロイを予定しています。

## 設計上の判断

### 認証

- 認証は JWT ではなくセッション方式を採用しました。サーバー1台・サーバーサイドレンダリングの構成では JWT の利点が生きず、ログアウトを確実に処理できるためです
- ログアウト時はセッションをデータベースから削除します。Cookie を消すだけでは、そのセッションIDが有効期限（ログインから7日）まで使えてしまうためです
- セッションIDは crypto/rand で生成し、Cookie には HttpOnly と SameSite=Lax を付けています。Secure 属性はローカル環境が HTTP のため現在は付けておらず、デプロイ時に有効にします
- ログイン確認は各ハンドラーに書かず、ミドルウェア（requireLogin）の一か所にまとめています。確認したユーザーIDはリクエストの context に入れてハンドラーへ渡します。グローバル変数に置くと、同時に届いたリクエストの間で値が混ざるためです
- ログアウトは POST で受け付けます。HTTP では GET はサーバーの状態を変えないメソッドとされており、GET にすると他のサイトのリンクを開いただけでログアウトさせられるためです
- ログイン失敗時は「ユーザーが存在しない」と「パスワードが違う」を区別せず、同じメッセージとステータスコードを返します
- 会員登録で名前が重複した場合は 409 を返します。名前がそのままログインIDになる構造のため、その名前が登録済みかどうかが分かってしまう点はトレードオフとして受け入れています

### データ設計

- アバターとアセットは一つのテーブルにまとめず、分けています。まとめると、対応関係・プリセット・改変履歴で「アバターでなければならない」という制約をデータベース側で表現できなくなるためです
- 他人のアバターに他人のアセットを結びつけられないようにする利用者の境界は、アプリケーション側で検査する方針です。データベースの複合外部キーで表すには中間テーブルにも利用者IDを持たせる必要があり、データの持ち方が冗長になるためです

### 画面

- 画面は html/template で描画し、利用者の入力を自動でエスケープすることで XSS を防いでいます

### テスト

- ハンドラーは、httptest で作ったリクエストとレコーダーを渡して直接呼び出し、ステータスコードなどを確認しています
- テストは、データベースに触れる前に処理が終わる経路（入力が空の場合、Cookie がない場合）と、データベースを使う経路（会員登録・ログインの成功と失敗）に分けています。前者はデータベースなしで実行できます
- データベースを使うテストは、開発用とは別のテスト用データベース（Docker Compose の testdb、ポート 5433）に接続します。各テストの開始時にデータを消すため、開発用と同じデータベースを使うと開発中のデータまで消えてしまうためです
- 各テストの開始時に `TRUNCATE users RESTART IDENTITY CASCADE` で全テーブルのデータを消し、IDの採番も戻しています。前に実行したテストのデータが残っていると、同じ名前で登録するテストが重複エラーになるなど、結果が実行順に左右されるためです
- テスト用データベースの接続先は環境変数 TEST_DATABASE_URL で指定します。設定されていない場合はデータベースを使うテストをスキップするため、テスト用データベースがない環境でも `go test ./...` は失敗しません
- ログイン失敗のテストは、「ユーザーが存在しない」場合と「パスワードが違う」場合を別々に用意しています。どちらも同じ 401 を返しますが、サーバー内では別の分岐を通るため、片方のテストだけではもう一方の分岐を確認できないためです
- 入力チェックは、両方が空の場合に加えて「名前だけ空」「パスワードだけ空」も別々に確認しています。両方が空の場合だけでは、条件の `||` を `&&` と書き間違えても気づけないためです
- requireLogin のテストでは、ステータスコードとリダイレクト先に加えて、次のハンドラーが呼ばれていないことも確認しています。リダイレクトした後に処理が止まらず次のハンドラーまで実行されてしまう不具合は、ステータスコードとリダイレクト先だけでは見分けられないためです

## 動かし方

```bash
# 1. .env を用意（.env.example をコピーし、パスワードを設定）
cp .env.example .env
# .env の中身:
#   POSTGRES_PASSWORD=任意のパスワード（開発用データベース）
#   TEST_POSTGRES_PASSWORD=任意のパスワード（テスト用データベース）

# 2. データベースを起動（開発用の db とテスト用の testdb が起動します）
docker compose up -d

# 3. スキーマとシードデータを投入
docker compose exec -T db psql -U seolhui -d maindb < schema.sql
docker compose exec -T db psql -U seolhui -d maindb < seed.sql

# 4. 接続情報を環境変数に設定（パスワードは .env と同じもの）
export DATABASE_URL="postgres://seolhui:<password>@localhost:5432/maindb"

# 5. サーバーを起動
go run .
```

PowerShell の場合は 3 と 4 を以下に置き換えてください。

```powershell
Get-Content schema.sql | docker compose exec -T db psql -U seolhui -d maindb
Get-Content seed.sql | docker compose exec -T db psql -U seolhui -d maindb
$env:DATABASE_URL = "postgres://seolhui:<password>@localhost:5432/maindb"
```

起動後、以下のページで確認できます。

- 会員登録: http://localhost:8080/signup
- ログイン: http://localhost:8080/signin
- アセット一覧・登録: http://localhost:8080/assets（ログインが必要です。ログアウトはこのページのボタンから行えます）

シードデータのユーザーはパスワードが設定されていないためログインできません。動作確認の際は、先に会員登録をしてからログインしてください（会員登録が終わるとログイン画面に移動します）。一覧にはログイン中の利用者が登録したアセットだけが表示されるため、会員登録した直後の一覧は空です。

テストは以下で実行できます。テスト用データベースを用意していない場合、データベースを使うテストはスキップされます。

```bash
go test ./...
```

データベースを使うテストも実行する場合は、テスト用データベースにスキーマを投入し、接続情報を TEST_DATABASE_URL に設定してください（パスワードは .env の TEST_POSTGRES_PASSWORD と同じもの）。

```bash
docker compose exec -T testdb psql -U seolhui -d testdb < schema.sql
export TEST_DATABASE_URL="postgres://seolhui:<password>@localhost:5433/testdb"
go test -count=1 ./...
```

PowerShell の場合:

```powershell
Get-Content schema.sql | docker compose exec -T testdb psql -U seolhui -d testdb
$env:TEST_DATABASE_URL = "postgres://seolhui:<password>@localhost:5433/testdb"
go test -count=1 ./...
```

`-count=1` は、テスト結果のキャッシュを使わずに毎回実行するための指定です。testdb には名前付きボリュームを設定していないため、`docker compose down` でコンテナを削除した後はスキーマを再投入してください。
